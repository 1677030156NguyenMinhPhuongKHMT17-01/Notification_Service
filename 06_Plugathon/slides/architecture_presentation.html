1. Ranh giới Dịch vụ & Quyền sở hữu Dữ liệu

Tuân thủ Luật 1 FIT4110: Tách biệt tuyệt đối dữ liệu, nghiệp vụ và phần cứng nguồn
docs/service_boundary.md

WE OWN — Notification Service sở hữu Inside Boundary

  • Async MQTT Consumer (mqtt_consumer.py): Subscribe campus.alerts (QoS 1, clean_session=False), đẩy việc sang ThreadPoolExecutor (MQTT_WORKER_THREADS=4).
  • Edge Contract Validation (models.py): Kiểm tra payload bằng Pydantic v2 event_adapter (extra="forbid", ^ALT-[0-9]{3,}$).
  • FastAPI REST Gateway (main.py): 7 endpoints tại cổng :8000, Bearer Auth & chuẩn lỗi RFC 9457.
  • Routing & Resilience Engine (store.py): SEVERITY_ROUTING, idempotency event_id, chống lệch thứ tự Q09, auto-retry 3×5s & manual retry.
  • Private PostgreSQL 15 (fit4110-db-lab06): Volume plugathon-db-data, bảng notifications (không ai ngoài service được đọc/ghi DB trực tiếp).
  • Channel Dispatcher (delivery.py): Tiêm lỗi FAIL_CHANNELS, stdout mock an toàn & opt-in HTTPS webhook ≤5s.

OUT OF SCOPE — Tuyệt đối không thực hiện Strict Boundary

  • 1. Không kết nối phần cứng / dữ liệu thô: Không đọc trực tiếp ESP32/IoT sensor, thẻ RFID Access Gate hay Camera Stream.
  • 2. Không chạy AI hoặc Rule nghiệp vụ: Không suy luận AI Vision, không đánh giá ngưỡng cảnh báo hay tự nâng cấp mức độ; mọi sự kiện đều do Core Business chuẩn hóa trước.
  • 3. Không chỉnh sửa hợp đồng đối tác: File contracts/core-business.openapi.yaml thuộc Nhóm 5 (chỉ đọc); mọi điểm lệch được ghi minh bạch ở known-issues.md.
  • 4. Không commit secret hay hard-code IP: Không lưu .env, bot token, webhook thật hoặc IP cố định vào Git/code (tuân thủ Luật 3).
Giao tiếp hợp lệ duy nhất: Upstream từ Core Business (Nhóm 5) qua MQTT campus.alerts (hoặc sync fallback POST /notifications); Downstream tra cứu qua REST Bearer Auth hoặc topic campus.alerts.dlq.

Channel Dispatcher & Postgres Ownership Runtime Mechanics

  • Zero-Secret Clean Clone: Mặc định chạy stdout mock có cấu trúc (ghi log kèm alert_id, correlationId), đảm bảo AI/giảng viên git clone chạy pass ngay không cần token.

  • Schema Persistence (PostgreSQL 15): Bảng notifications lưu notification_id, event_id UNIQUE, target_channels JSONB, status, retry_count, error_detail, event_timestamp.
  • Build-Stage Fallback: Khi DATABASE_URL rỗng, tự dùng MemoryBackend để chạy pytest cô lập ngay trong Docker build stage.

4. Chịu lỗi, Dead-Letter Queue (campus.alerts.dlq) & Bảo vệ Q09

Xử lý tất định lỗi hợp đồng, lỗi kênh gửi tạm thời, sự kiện trùng & sự kiện đến muộn
Q05 · Q07 · Q08 · Q09

1. Schema Fail (Q08) No Retry → DLQ

  • Trigger: JSON lỗi cú pháp, thiếu trường, sai regex ALT-xxx, extra="forbid" (như alert.deleted / EXTREME).
  • Hành vi: Reject ngay ở consumer với retry_count = 0 (không lãng phí retry).
  • DLQ Output (campus.alerts.dlq): Envelope gồm topic, reason: "SCHEMA_VALIDATION_FAILED", error_detail, source_topic, original_payload, failed_at.

2. Channel Fail (Q07) Retry → DLQ → Retry API

  • Trigger: Kênh nằm trong FAIL_CHANNELS (như sms) hoặc webhook ngoài lỗi.
  • Auto-Retry: Thử tối đa MAX_RETRIES=3 lần, cách nhau RETRY_INTERVAL_SECONDS=5s.
  • Restart Safe: Khi khởi động lại, store.init() chuyển bản ghi kẹt retrying → failed.
  • DLQ & Recovery: Quá hạn → failed + publish DLQ MAX_RETRIES_EXCEEDED; sau khi sửa lỗi gọi POST /notifications/{id}/retry → delivered.

3. Idempotency & Out-of-Order Q05 / Q09 Guard

  • Q05 Duplicate event_id: Khóa event_id UNIQUE chặn gửi lặp kể cả khi container khởi động lại: REST trả 409 Conflict, MQTT skip an toàn.
  • Q09 Out-of-Order: Nếu alert_id đã ghi nhận alert.resolved với event_timestamp mới hơn event đến sau (T < T_resolved), từ chối phát kênh.
  • Audit Log: Ghi bản ghi với status: "duplicate_ignored", sent: false, error_detail: "SUPPRESSED_OUT_OF_ORDER:...".
Trạng thái vòng đời chuẩn (DeliveryStatus): queued → retrying (nếu gặp lỗi tạm thời) → delivered | failed (và đẩy DLQ) | duplicate_ignored (khi bị triệt tiêu bởi Q09).

6. Tích hợp Plug-a-thon Mạng Chung (class-net + Broker Lớp)

Chuyển đổi sang hạ tầng chung bằng file overlay — không sửa code, không đụng cổng 1883
docker-compose.external-broker.yml

Cơ chế Overlay docker-compose.external-broker.yml Dual-Homed Network

  • Tắt Mosquitto cục bộ tránh đụng cổng: Gán profiles: ["local-broker"] và ports: !override [] cho service mqtt-broker.
  • Giữ DB cô lập riêng: Container db chỉ nằm trên plugathon-internal, tuyệt đối không phơi sang mạng lớp class-net.
  • Phơi API lên mạng lớp: Service api gắn cả plugathon-internal lẫn class-net (external: true) với DNS alias notification-service.
  • Ghi đè Broker động qua ENV (Luật 3): MQTT_BROKER_URL=${MQTT_BROKER_URL:-mqtt://192.168.1.51:1883} và MQTT_CLIENT_ID=notification-service-g7-plugathon.

Lệnh ghép & Khai báo phía Đối tác Inter-Group Onboarding

  • Tạo mạng dùng chung (1 lần): docker network create class-net
  • Khởi chạy chế độ Plug-a-thon:
    MQTT_BROKER_URL=mqtt://192.168.1.51:1883 docker compose -f docker-compose.yml -f docker-compose.external-broker.yml up -d --build --wait
  • Core Business (Nhóm 5) kết nối: Publish alert.* lên topic campus.alerts của broker lớp; fallback HTTP gọi http://notification-service:8000/notifications.
  • Analytics / Dashboard: Truy vấn GET http://notification-service:8000/notifications/recent với header Authorization: Bearer <AUTH_TOKEN>.
Kiểm tra ghép mạng thành công: GET /ready bắt buộc trả HTTP 200 với dependencies.database.ready: true và dependencies.mqtt.connected: true trên địa chỉ broker lớp.
